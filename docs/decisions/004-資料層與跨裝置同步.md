# 004 資料層與跨裝置同步

- 日期：2026-11-25
- 狀態：部分定案。本機儲存已定案；**自動同步為 MVP 必要功能，同步機制待研究後再定**。

## 已定案
- **本機主資料庫**：IndexedDB（Dexie 封裝），由背景程式（background service worker）集中管理。content script 一律透過 `chrome.runtime.sendMessage` 存取，因為在 content script 直接開 IndexedDB 會寫到「目標網站」的儲存空間。
- **輕量設定與高亮索引**：`chrome.storage.local`（設定、生詞原形集合，讓網頁端快速讀取並監聽變更）。
- **自動跨裝置同步是 MVP（第一個能用的版本）的必要功能**。理由：Aya 本人就是頻繁在 Mac 與 Windows 之間切換的使用者，手動匯出匯入不可接受。
- **同步不可以經過 Aya 的伺服器**（鐵律 1）。

## 待研究（同步機制）
| 候選 | 已知優點 | 已知問題 |
|---|---|---|
| `chrome.storage.sync`（Chrome 內建帳號同步） | 零設定，登入同一 Chrome 帳號就同步 | 總容量 100 KB、單項 8 KB、512 項、寫入頻率有限；完整單字本放不下 |
| 使用者自己的雲端硬碟（如 Google Drive 的 app 專屬資料夾、OneDrive、Dropbox） | 容量足夠；一般使用者有帳號 | 要做 OAuth 登入；要確認權限範圍是否需要 Google 審查；衝突合併要自己做 |
| WebDAV（使用者自填伺服器） | 不綁特定公司，容量足夠 | 一般使用者沒有 WebDAV，設定門檻高，不符合「在意但不折騰」的目標使用者 |
| 混合：`chrome.storage.sync` 存精簡狀態 ＋ 雲端硬碟存完整資料 | 小資料零設定即同步，大資料有完整備份 | 兩條同步路徑，複雜度最高 |

不論選哪個，都需要：每個單字帶修改時間的合併規則、刪除用墓碑標記（tombstone，記錄「已刪除」而不是直接消失，避免另一台又同步回來）、離線時的佇列。
